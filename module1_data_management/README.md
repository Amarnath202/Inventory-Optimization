# Module 1 — Dataset Processing, Validation & Database Setup

**Project:** Inventory Optimization and Excess Stock Management System for Retail Stores  
**Dataset:** Robins Hypermarket — THRESHOLD-BASED synthetic dataset  
**Database:** `inventory_optimization_db2` (PostgreSQL)

---

## Overview

Module 1 establishes the data foundation for all downstream modules. It inspects, validates, preprocesses, and loads four source CSVs into a normalized PostgreSQL schema, then builds a `daily_demand` aggregate table for use by the Demand Forecasting module (Module 2).

## Quick Start

### 1. Environment Setup

Use the canonical root `README.md` for Python environment creation, dependency
installation, and the shared root `.env.example` / `.env` configuration. Run the
Module 1 commands below from the repository root using `.venv\Scripts\python.exe`.

### 2. Run All Phases in Order

```powershell
# Always set PYTHONUTF8=1 on Windows to avoid cp1252 encoding issues
$env:PYTHONUTF8=1

.\.venv\Scripts\python.exe module1_data_management\src\inspect_data.py
.\.venv\Scripts\python.exe module1_data_management\src\validate_data.py
.\.venv\Scripts\python.exe module1_data_management\src\preprocess.py
.\.venv\Scripts\python.exe module1_data_management\src\build_schema.py
.\.venv\Scripts\python.exe module1_data_management\src\load_database.py
.\.venv\Scripts\python.exe module1_data_management\src\build_daily_demand.py
.\.venv\Scripts\python.exe -m pytest module1_data_management\tests -q
```

> **Note:** All scripts are idempotent. Re-running `load_database.py` uses
> `ON CONFLICT DO NOTHING` and skips rows already present. Re-running
> `build_daily_demand.py` truncates and rebuilds `daily_demand` only.

## Database Schema

### Tables

| Table | PK | Rows | Description |
|---|---|---:|---|
| `supplier` | `supplier_id` | 200 | Supplier master |
| `product` | `product_id` | 3,046 | Product master |

### Key Relationships

```
supplier ──< product_supplier >── product
supplier ──< inventory_batch >── product
sale ──< sale_item >── product
              sale_item >── inventory_batch
product ──< daily_demand
```

## Design Decisions

| Decision | Rationale |
|---|---|
| `sale` header + `sale_item` lines | Normalises bill-level data (date, payment) from line-level |
| `product_supplier` junction table | Forward-compatible with multiple suppliers per product (Procurement Agent) |
| `daily_demand` as materialized table | Fast reads for LightGBM feature matrices in Module 2 |
| `CHUNK_SIZE = 200,000` for sales | Bounds memory usage for the 526 MB sales file |
| `ON CONFLICT DO NOTHING` in loader | Safe idempotent reruns without data loss |
| `Lead_Time_Date_Difference_Days` derived | Date arithmetic only; kept separate from modelled `Supplier_Lead_Time_Days` |
| No calendar gap-filling in `daily_demand` | Only observed sale dates included; no phantom zeros |

## Configuration

Key settings in [`config/settings.py`](config/settings.py):

```python
DB_NAME    = "inventory_optimization_db2"
DB_HOST    = "localhost"
DB_PORT    = 5432
CHUNK_SIZE = 200_000       # Rows per chunk for sales processing
RAW_DIR    = data/raw/     # Source CSVs — never modified
PROC_DIR   = data/processed/
SQL_DIR    = sql/
```

Credentials are loaded from the repository-root `.env`, created from the root
`.env.example` as described in the root `README.md`.
